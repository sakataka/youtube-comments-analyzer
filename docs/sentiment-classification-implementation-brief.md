# 感情判定を三段階化する実装指示書

## 依頼文

このリポジトリの感情判定を、ルール判定、ローカル感情分類モデル、生成AIによる補助判定の三段階へ変更してください。

既存の日本語感情分類モデルを利用し、このアプリ専用モデルの学習や大量の教師データ収集は行いません。

実装前に現行の判定経路、DB、レポート生成、レビューセンター、Codex app server連携を確認し、既存runの再判定と失敗時の縮退動作まで含めて完成させてください。

変更後は関連テスト、build、E2E、実データでの再判定を行い、通常のcommitとpush、LocalWebバックエンドの再起動、live API確認まで完了してください。

## 目的

現行の単語ルールは、明示的な評価表現を高速かつ再現可能に判定できる一方、反語、引用、慣用句、評価対象の違いを誤りやすい状態です。

たとえば「二宮またかわいくなってないか…？」は称賛ですが、現在は「かわい」の直後に否定表現があるためネガティブになります。

「下手にアドリブするより」は人物を下手だと評価していませんが、現在はネガティブ語として拾われます。

三段階化では、ルールの説明可能性を残しつつ、既存の日本語分類モデルで文全体を判定し、両者だけでは確定できないコメントに限って生成AIを使います。

## 判定パイプライン

### 第一段階のルール判定

現行の `backend/app/sentiment.py` を残し、各コメントについて動画全体と人物別のルール判定を生成してください。

ルール判定は最終結果ではなく、次の情報を持つ一次判定として扱います。

- ラベル
- 確度
- 一致した評価語
- 否定表現
- 対象範囲
- 曖昧性フラグ

反語、疑問符、引用、複数節、対比、慣用句を検出した場合は、高確度のポジティブまたはネガティブとして確定せず、曖昧性フラグを立ててください。

少なくとも次の表現を回帰テストへ追加してください。

- `二宮またかわいくなってないか…？？`：ポジティブ
- `下手にアドリブするよりムズいんじゃないか`：ネガティブではない
- 引用中に `残念！` があるが、コメント末尾で面白さを評価している文：ネガティブではない
- 実現可能性について `無理` と述べる文：動画へのネガティブと即断しない
- `板倉はもういい、面白くない。`：ネガティブ
- `最高だけど少し苦手`：混合

### 第二段階のローカル分類

全コメントを既存の日本語感情分類モデルでバッチ推論してください。

ローカル分類は外部APIへコメントを送信せず、Apple Silicon上のローカルPythonプロセスで完結させてください。

モデルは実装開始時にレジストリ、モデルカード、ライセンス、ラベル定義、依存関係の最新状態を確認し、次の条件で二つ以上を比較してください。

- 日本語のポジティブ、ニュートラル、ネガティブ分類を提供する
- 商用利用を妨げないライセンスである
- モデルカードに学習データまたは評価方法の説明がある
- Apple SiliconのCPUまたはMPSで実行できる
- 入力を外部サービスへ送らない
- モデルとrevisionを固定できる

比較対象には、WRIMEなど日本語SNS由来データで調整されたBERT系モデルと、日本語レビューまたは一般文向けのBERT系モデルを含めてください。

採用モデルは、既存fixtureと後述する小規模評価セットに対するmacro F1を第一基準とし、反語、引用、慣用句での誤判定数を第二基準として決めてください。

推論速度は記録しますが、モデル選定の第一基準にはしません。

ローカルモデルの三分類は、既存の五分類へ次のように統合してください。

- モデルが明確なポジティブ、ニュートラル、ネガティブを返し、ルール判定と矛盾しない場合はそのラベルを採用する
- ルールとモデルがポジティブとネガティブに分かれた場合は `unclear` として生成AIの対象にする
- 一つのコメント内に独立した肯定節と否定節がある場合は `mixed` 候補として生成AIの対象にする
- モデルの最大確率が採用モデルの検証で定めた閾値未満の場合は `unclear` として生成AIの対象にする
- 人が保存したoverrideは常に全自動判定より優先する

確率の閾値を恣意的に固定せず、評価セット上で誤確定を抑えられる値を選び、テストへ根拠を残してください。

### 第三段階の生成AI判定

生成AIへ送るのは、次のいずれかに該当するコメントだけにしてください。

- ルールとローカルモデルが矛盾する
- ローカルモデルの確度が閾値未満である
- 反語、皮肉、引用、複数対象、対比を含む
- `mixed` または `unclear` の候補である
- 動画全体と人物別で評価対象を分離できない

生成AIには、コメント本文、動画タイトル、判定対象、対象人物名、ルールの根拠、ローカルモデルの各ラベル確率を渡してください。

投稿者属性の推測や、コメントに存在しない背景事情の補完は禁止してください。

生成AIは、対象、最終ラベル、確度、短い理由をJSONで返すようにしてください。

生成AIが失敗またはタイムアウトした場合は、ルールとローカルモデルの統合結果を保存し、確定できない項目を `unclear` としてレビューセンターへ残してください。

## データと互換性

既存の `sentiment_labels` と `sentiment_overrides` を中心に実装し、不要なDB移行は避けてください。

各判定の `method` は少なくとも `rule`、`local_model`、`hybrid`、`ai`、`human` を区別できるようにしてください。

`evidence_json` には次を保存してください。

- ルールで一致した語と対象範囲
- ローカルモデルのIDとrevision
- ローカルモデルの各ラベル確率
- 統合判定の理由
- 生成AIを使った場合の短い理由

レポートの感情セクションには、ローカルモデルの利用状態、モデルID、revision、AI補助件数、判定method別件数を追加してください。

既存runはコメントを再取得せず、保存済みコメントから感情だけを再判定できるAPIまたは既存継続処理を拡張してください。

再判定時も `sentiment_overrides` を消さず、人が修正したラベルを最後に再適用してください。

モデルを読み込めない場合はルール判定へ縮退し、レポート自体を失敗させないでください。

## 設定と依存関係

Python依存関係は既存方針に従って管理し、無関係なパッケージを更新しないでください。

モデルID、revision、確度閾値、ローカルモデルの有効無効は設定として管理し、コード中へ散在させないでください。

モデルファイルはGitへ追加せず、ローカルキャッシュを利用してください。

初回ダウンロード失敗、オフライン、破損キャッシュ、推論例外をそれぞれ通常の縮退経路で扱ってください。

モデルの遅延読み込みとプロセス内再利用を行い、コメントごとにモデルを再初期化しないでください。

## 小規模評価セット

大量の学習データは作成しません。

既存fixtureに加え、実際に誤判定が見つかったコメントを中心に、動画全体の正解ラベルを持つ評価fixtureを追加してください。

初期件数は50件以上を目安とし、次の種類を意図的に含めてください。

- 明示的な称賛
- 明示的な否定
- 事実記述
- 反語
- 引用
- 慣用句
- 否定の否定
- 肯定と否定の混在
- 評価対象が動画ではないコメント
- 短すぎて判断できないコメント

このfixtureは再学習用ではなく、モデル選定と将来の回帰テストに使用してください。

採用前後について、少なくともラベル別precision、recall、F1、macro F1、混同行列を出してください。

全体accuracyだけで採用を判断しないでください。

レビューセンターで人が修正した内容を自動的に学習へ使わないでください。

将来fixtureへ追加できるJSONL形式でエクスポートできれば十分です。

## UI

コメント一覧では、最終ラベルに加えて判定方法と確度を確認できるようにしてください。

通常表示を過密にしないため、判定方法と確度は詳細表示またはツールチップでも構いません。

レビューセンターには、ルールとローカルモデルの不一致、低確度、生成AI失敗を優先表示してください。

人がラベルを修正したコメントは、再判定後も人の修正であることを表示してください。

## テスト

次のテストを追加してください。

- ルール判定の反語、引用、慣用句、否定表現
- ローカルモデル出力の正規化
- ルールとモデルの一致、不一致、低確度、混合候補の統合
- 生成AIを呼ぶ条件と呼ばない条件
- ローカルモデルまたは生成AI失敗時の縮退
- 人のoverrideが最優先されること
- 既存runを再判定してもコメントとoverrideが失われないこと
- レポートとコメントAPIにmethod、確度、モデル情報が反映されること
- コメント画面とレビューセンターの表示

実モデルを使うテストと、固定出力のfake modelを使う単体テストを分けてください。

通常のCIではfake modelによる決定的なテストを実行し、実モデルの比較評価は明示コマンドで再実行できるようにしてください。

## 受け入れ条件

- ルール、ローカルモデル、生成AIの三段階が独立して失敗できる
- 生成AIへ送るコメントが判定困難な項目に限定される
- 既存runをコメント再取得なしで再判定できる
- 人のoverrideが再判定後も維持される
- 採用モデルとrevisionがレポートから確認できる
- モデル選定結果をmacro F1と誤判定例で説明できる
- 反語、引用、慣用句の既知誤判定が回帰テストで防止される
- ローカルモデルまたは生成AIが利用できなくてもレポートを表示できる
- 既存の人物抽出、コメント検索、感情フィルター、高評価順を壊さない
- Pythonテスト、TypeScript build、E2Eが成功する
- LocalWebのlive APIとブラウザ画面で再判定結果を確認できる

## 実装完了時の報告

完了報告には次を含めてください。

- 採用モデル、revision、ライセンス
- 比較したモデルと評価結果
- 三段階の判定件数
- 生成AIへ送った件数と割合
- 既存runの再判定結果
- 既知の誤判定例がどう変わったか
- 実行したテストと結果
- commit、branch、push結果
- LocalWebバックエンド再起動とlive確認結果
